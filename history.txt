  1. Nostr in one minute

  - Your identity is a keypair. The keys are secp256k1, the same curve Bitcoin
    uses. The secret key is usually shown as nsec1… and the public key as
    npub1…. There are no accounts, passwords or servers that own you; whoever
    holds the nsec is you.
  - Everything is a signed event. An event is a JSON object with pubkey,
    created_at, kind, tags, content, id and sig. The id is the SHA-256 of a
    canonical serialization of the fields, and sig is a Schnorr (BIP-340)
    signature over that id.
  - Relays are dumb pipes. They're WebSocket servers like wss://relay.damus.io
    that store and forward events. Clients publish events to relays and
    subscribe with filters such as "events of kind X that tag pubkey Y".
  - NIPs ("Nostr Implementation Possibilities") are the specs, numbered by
    feature.

  So "logging in with Nostr" just means: prove you control a pubkey by signing a
  challenge the website gave you.

  2. The problem NIP-46 solves

  Signing needs the nsec. Pasting your nsec into every website is terrible, and
  browser extensions (NIP-07) don't work on mobile. NIP-46 ("Nostr Connect", or
  a "bunker") keeps the key in a separate program, the remote signer. Apps send
  it signing requests over Nostr relays.

  Mechanics:

  ┌────────────┬─────────────────────────────────────────────────────────────┐
  │   Aspect   │                           Detail                            │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Transport  │ Kind 24133 events published to relays                       │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Encryption │ Content encrypted with NIP-44 per the spec (NIP-04 is       │
  │            │ older; see the warnings below)                              │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Request    │ Client → signer: {"id": "<random>", "method": "...",        │
  │            │ "params": [...]}, with a p tag pointing to the signer       │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Response   │ Signer → client: {"id": "<same>", "result": "...",          │
  │            │ "error"?: "..."}, with a p tag pointing to the client       │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Client key │ The app makes a throwaway keypair just to talk to the       │
  │            │ signer. It never sees your nsec.                            │
  └────────────┴─────────────────────────────────────────────────────────────┘

  Methods your signer will need: connect, get_public_key, sign_event and ping.
  Optional ones: nip04_*/nip44_* encrypt/decrypt, switch_relays and logout.
  Unknown methods must get an error response.

  Two ways to pair:
  - bunker://<signer-pubkey>?relay=wss://…&secret=<one-time>: the signer creates
    this URL and the user pastes it into the app. The app then sends connect.
  - nostrconnect://<client-pubkey>?relay=…&secret=…: the app shows this URL
    (often as a QR code) and the signer scans it.

  3. How Stacker News uses it

  Stacker News only accepts bunker:// tokens (or a NIP-05 address), not
  nostrconnect://. So your signer must generate a bunker:// URL. The flow, from
  the code:

   Browser (SN page JS, NDK lib)      Relay(s)            YOUR SIGNER (holds
  nsec)
          |                              |   <-- subscribed to kind 24133, #p =
  signer pubkey
    1. user pastes bunker://…            |                         |
    2. SN server → k1 challenge          |                         |
       (GraphQL createAuth)              |                         |
    3. connect [signer, secret] -------->|------------------------>| check
  secret (one-time)
          |<-----------------------------|<-------- "ack" ---------|
    4. get_public_key ------------------>|------------------------>|
          |<-----------------------------|<------ user pubkey -----|
    5. sign_event({kind:27235, ...}) --->|------------------------>| (approve?)
  sign with nsec
          |<-----------------------------|<----- signed event -----|
    6. POST signed event to SN server (next-auth "nostr" provider)
       server checks: id hash ✓, Schnorr sig ✓, tags[0] == ["challenge", k1] ✓
       → k1 deleted (anti-replay) → find/create user by pubkey → session cookie

  The event Stacker News asks you to sign:

  { kind: 27235, created_at: now,
    tags: [["challenge", k1], ["u", "https://stacker.news"], ["method", "GET"]],
    content: "Stacker News Authentication" }

  Two non-obvious points:
  - The NIP-46 client is Stacker News's frontend JavaScript running in your
    browser, not their server. Their server only ever sees the final signed
    event.
  - If the pubkey is new, Stacker News creates an account, but only from the
    /signup page, which is the URL task.md uses. From /login, an unknown key is
    rejected because of a signin cookie check. A brand-new key therefore works
    for the demo if you start at /signup.

  4. What you have to build

  1. Key management: create a new keypair or import an nsec, and store it
     encrypted at rest. NIP-49 (ncryptsec, password-based) is the standard for
     this.
  2. A NIP-46 signer daemon: connects to relays, subscribes to kind 24133 events
     addressed to it, decrypts, dispatches methods, signs, encrypts and
     replies.
  3. bunker:// URL generation with a one-time secret.
  4. (Nice to have) A request-approval step: show "Stacker News wants to sign a
     kind 27235 event" and let the user approve or deny.
  5. The demo: a recorded end-to-end login, plus the README and your AI chat
     logs.

  5. Gotchas to plan for

  These were reported by other people who built signers against Stacker News. I
  haven't reproduced them yet; we'll confirm them when testing.

  - Encryption mismatch: Stacker News uses NDK ^2.12.2 (I checked its
    package.json), which reportedly encrypts NIP-46 traffic with NIP-04, not the
    NIP-44 the spec requires. A robust signer detects which one arrived (NIP-04
    ciphertext contains ?iv=) and replies in the same scheme.
  - Empty first param: Stacker News's connect request may send an empty
    signer-pubkey param, so don't reject it on that basis.
  - Single-use secrets: a token whose secret was already used will hang. Stacker
    News even shows the hint "Make sure you used a fresh token".
  - The signer must be running and listening before you paste the token. Stacker
    News waits about 10 s before showing that hint.
  - Signer pubkey vs user pubkey: the spec says these can differ. Using the same
    key for both is simplest; a separate signer key is cleaner. This is a
    design choice to document.

● Right, it isn't NIP-46 yet. Today the CLI uses only:

  - NIP-01: the event format (id, signature) and the relay messages (["EVENT",
    …] → ["OK", …]).
  - NIP-19: the npub/nsec/nevent encodings.

  The difference is who asks for the signature:

  Now (local signing):
    you ──► kazna post ──► signs with your key ──► publishes to relays

  NIP-46 (remote signing):
    Stacker News page ──"please sign this"──► relay ──► kazna bunker
    (no access to your key)                             (has your key, signs it)
    Stacker News page ◄──"here's the signed event"── relay ◄──┘

  With NIP-46, kazna stops being the app that decides what to publish. It
  becomes a service that waits for another app to send requests: connect,
  get_public_key, sign_event. Those requests are encrypted kind 24133 events
  sent through relays. The app never sees your key, only the signed results.

  Most of today's code carries over: Identity signs, Event builds and verifies,
  and the relay connection is reused. The NIP-46 step adds:

  1. A long-running subscription to the relay (listening, instead of publishing
     once and leaving).
  2. Encryption of the messages (NIP-44, plus NIP-04, which Stacker News may
     still use).
  3. A request handler for those methods.
  4. The bunker:// link you paste into Stacker News.

  That's why I said the local relay will be useful: while building it, I can run
  the signer plus a small script that plays Stacker News's part, entirely on
  your machine, without touching public relays. For the real Stacker News demo
  we'll use public relays, because Stacker News's page runs in your browser and
  has to reach the same relay as the signer. Pointing the browser at the local
  relay (ws://localhost:7777) might work, but I haven't tested it.

  What I confirmed in Stacker News's login code (NDK 2.12.2)

  I read the exact version Stacker News ships. These facts shape the design:

  1. It encrypts with NIP-04 by default. It switches to NIP-44 only if a reply
     arrives in NIP-44. So we implement both, detect the scheme from the request
     (NIP-04 ciphertext contains ?iv=), and reply in the same one.
  2. Its connect sends ["", secret]. The first param is empty, so we must not
     reject that.
  3. It only accepts "ack" as the connect result. The newer spec also lets the
     signer echo the secret back, but NDK would treat that as a failure.
  4. It then calls get_public_key. This means the signer's own key can be
     different from your identity key.
  5. It creates a fresh client key on every login. So every login needs a fresh
     bunker:// secret.
  6. For sign_event it uses only the returned sig and computes the event id
     itself. So we must sign with exactly the pubkey we reported from
     get_public_key.

● Congrats on the working login! Yes, you can post on Stacker News right now,
  and nothing is missing from kazna for that. The bunker isn't involved anymore.

  Why: Stacker News uses Nostr only to prove who you are at login. Once it
  checked the signed challenge, it gave your browser a normal session cookie.
  From then on, posts, comments and zaps go through the website and its own
  database, not as signed Nostr events. So:

  - Post on Stacker News in the browser as usual.
  - You can stop the bunker with Ctrl+C. Your Stacker News session stays alive.
  - You need the bunker again only to log in again, for example after logging
    out or on another browser. Run kazna bunker vavilov and paste the new link;
    each link works once.

  The "blocking" part: bunker is meant to be a long-running service, like
  ssh-agent. It waits for requests and shows the y/N prompts, which need a
  terminal. It doesn't stop you doing other things. Open a second terminal and
  kazna post vavilov -m "…" works while the bunker is running, because each
  command is its own container reading the same key file.

  Keep in mind that kazna post and a Stacker News post are different things:

  ┌─────────────────────┬─────────────────────────────┬────────────────────┐
  │                     │         kazna post          │  Post on Stacker   │
  │                     │                             │        News        │
  ├─────────────────────┼─────────────────────────────┼────────────────────┤
  │ Where it goes       │ Nostr relays (njump, Damus, │ Stacker News's     │
  │                     │  Primal…)                   │ site               │
  ├─────────────────────┼─────────────────────────────┼────────────────────┤
  │ Signed with your    │ Yes, every note             │ No, it uses your   │
  │ Nostr key           │                             │ session            │
  └─────────────────────┴─────────────────────────────┴────────────────────┘

  One possible exception: Stacker News has an optional "crosspost to Nostr"
  setting that publishes your post as a Nostr note too, and that would need a
  signer. From the code I read, it looks for a browser extension. I haven't
  checked whether it can use a bunker.
